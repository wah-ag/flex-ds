# CLAUDE.md

Flex DS is a design system. Design tokens are exported from Figma, built with
Style Dictionary (`npm run build:tokens`), and consumed by components in
`src/components/`, which are documented in Storybook.

## The system

- Tokens are the only source of visual values. Every colour, space, radius,
  shadow and font value references a token.
- `tokens/` is the Figma export. Never hand-edit anything in it. The plugin
  owns those files. If a value is wrong, fix it in Figma, re-export, and
  rebuild. A patch applied here is silently destroyed by the next export.
- `build/` is generated by `npm run build:tokens`. Never edit it and never
  commit it — it is gitignored, and `tokens/` is what ships.
- Three layers, consumed in one direction: core primitives → semantic roles →
  composite styles (typography, elevation). Components use semantic tokens
  only. A component referencing `--color-blue-500` is wrong; it should
  reference `--color-text-brand` or `--color-background-interactive-*`.
- Modes come from Figma. Semantic colour has `on-light` and `on-dark`; the type
  scale has `web`, `mobile` and `back-office`. A token that exists in one mode
  and not another is a design gap — report it rather than filling it in.
- Re-run `npm run build:tokens` after any change to `tokens/`. Both Storybook
  scripts do this for you.

## Naming

- Token names come from Figma. Do not rename in the pipeline.
- Token names read category, then property, then role:
  `color-text-brand`, `spacing-padding-md`, `border-radius-sm`, `size-icon-lg`.
- Semantic colour reads `color-<surface>-<role>-<variant>`:
  `color-text-disabled-primary`, `color-border-brand-secondary`.
- Mode is a file, never a suffix. There is no `-dark` or `-mobile` in a token
  name; the same name resolves differently per mode.
- An `a` suffix means the token carries an alpha channel. If it exports opaque,
  it is misnamed — report it.
- Components: PascalCase, one folder per component in `src/components/`.
- Prop names match the Figma property names exactly. If Figma says `size`, the
  prop is `size`. If a name must change because it conflicts with another tool
  or dependency, do not rename it silently — write up every suggested name
  under `docs/` for review.

## Components

Components live in `src/components/`, one folder each, with their stories
beside them. `ButtonCTA` is the first; these rules apply to it and to every
component after it.

- Every component covers every interaction state the product uses, as
  applicable: default, hovered, pressed, focused, disabled, and destructive
  (error cases). The token layer has a full disabled and interactive
  vocabulary — use it rather than dimming something yourself.
- Every variant and every state has a story.
- A component's props are its documented API. Undocumented behaviour is a bug.
- Import the component. Never copy its styles into another component.
- Build with subcomponents, following atomic design. Organisms in particular
  are composed from smaller components. When part of a component is (or could
  be) used elsewhere, extract it into its own subcomponent in
  `src/components/`, then import it back into the parent.
- Consume a platform entry point (`build/css/index.css`,
  `index-mobile.css`, `index-back-office.css`), never an individual token file.
- Dark mode is `[data-theme="dark"]` on an ancestor. Never branch on theme in
  JavaScript, and never read a token value to decide something — let the
  cascade resolve it.
- Stories derive their content from the build output, never from a hand-kept
  list of token names. A list typed into a story is wrong the day a token is
  added, and nobody notices. `stories/lib/tokens.js` parses `build/css/*.css`
  for exactly this reason.

## Roles

- The engineer (the Developer) builds and fixes. It never verifies its own
  work.
- QA tests and reports. It never repairs.
- DevOps deploys to Vercel and writes the production Storybook link.
- A human approves. No agent approves its own work, ever.
- `token-runner` owns the Figma sync — branch, build, summarise the diff in
  designer language, then stop for review or open a PR. It holds Bash and Read
  only, deliberately: it can never edit a token.
- **No agent pushes to main.** Agents open pull requests. Exactly two merges
  are delegated to agents; a human merges everything else, including every
  token sync:
  - The Developer merges its own component branch into `staging`.
  - DevOps merges a component branch into `main`: one pull request per
    component, plus any component it composes that is not yet on `main`. It
    merges only after a human has approved that pull request, and only once
    QA has passed every Staging Testing row for every component in it.

## Common failures to avoid

- Inventing a token that does not exist. Report the gap instead and stop.
- Copying a component's styles instead of importing the component.
- Raw hex, px, or font values inside a component file.
- Adding a dependency to solve a problem the existing stack already solves.
- Hand-editing `tokens/` or `build/`, or working around the rule with `sed`,
  a redirect, or a script.
- Committing a token sync together with unrelated work. Stage `tokens/` alone.
- Reading a green build as proof that an export is sound.
- Filling in a missing mode so a table looks complete.
- Summarising a token diff in diff language. "Brand blue 600 got darker,
  `#3676E0` → `#3260AC`" is the unit of communication here, not "line 47
  changed".

- Install required font and load properly from Google Font CDN

## Icon
- Icons come from Lucide (https://lucide.dev/icons/) and nowhere else. Install
  the Lucide package for the component framework (e.g. `lucide-react`) and
  import each icon by name. Never paste SVG markup into a component, and never
  mix in another icon set.
- Size icons with the `size-icon-*` tokens and colour them through
  `currentColor`, so they follow the semantic text colour of their parent.
- If a design needs an icon Lucide does not have, report it rather than
  drawing or importing one.
